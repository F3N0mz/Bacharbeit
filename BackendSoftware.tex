\section{Microcontroller Programming}\label{sec:Backenddev}
\textbf{Note}: For programming part, all the source code is available under authors Github Repository here \cite{Github_src}. Code for this section to be found in the \textbf{ESP32/Pillspender} folder of the repository.

As mentioned before, the microcontroller of choice is an ESP32 S3 DevKitC-1 N16R8 \cite{microcontroller}. This microcontroller has 16MB Octal \ac{SPI} flash memory and 8MB of \ac{PSRAM}. It supports Arduino framework, which makes it easier to program, compared to many libraries published by the developers (such as Espressif's own ESP-IDF) as it abstracts away some low-level programming through helper libraries (such as \texttt{stepper.h} for charging/discharging of motor coils). The code consists of 2 separate parts: The first part is responsible for communication with stepper motor. It means that it covers all the functions required for stepper motor to rotate a necessary amount of steps to move the next chamber into position. The second part is responsible for \ac{BLE} interface and establishing the device as a \ac{BLE} host.

The \textbf{main.cpp} file is rather minimal because the code was semantically split also in \textbf{\ac{BLE}} and \textbf{Motor Control} parts. Here is a short overview of the contents of main.cpp file:
\begin{lstlisting}[style=cppstyle, caption={Main Arduino Loop Code}, label={lst:mainLoop}]
	#include <Arduino.h>
	#include "motorcontrol.h"
	#include "BTooth.h"
	
	void setup() {
		Serial.begin(115200);
		
		motorSetup();     // stepper + pins
		bleSetup();       // BLE GATT server
	}
	
	void loop() {
		bleLoop();
		MotorStatus motorStatus = motorLoop(); // Call motorLoop and get its status
		if (motorStatus == MOTOR_JUST_COMPLETED) {
			bleNotifyDispenseComplete(); 
		}
		delay(10);
	}
\end{lstlisting}
As seen in the code block \ref{lst:mainLoop}, \textbf{main.cpp} file includes 3 libraries, 2 of which are custom (\texttt{motorcontrol.h} and \texttt{BTooth.h}) and one is a built-in \texttt{Arduino.h} library. Specifics of Arduino microcontroller programming is that main body is divided into \texttt{setup()} and \texttt{loop()} functions, unlike standard C/C++ file where only \texttt{int main()} exists. Effectively, this is the same thing as C code having a \texttt{while(TRUE)} loop inside the \texttt{main()} function.
\subsection{Stepper motor controls}

Controls of a stepper motor are handled by 2 files: \textbf{motorcontrol.cpp}, which contains the implementation itself, and \textbf{motorcontrol.h}, which contains public interface of the motor control module. The motor control implementation is split into 2 (.cpp and .h) files is not only a stylistic choice (splitting declaration action from definition action) but also positively affects code readability, compilation time and prevents accidental redefinition of functions. For example this code block \ref{lst:motorcontrolh} shows the contents of the \textbf{motorcontrol.h} file. The first 2 lines (\texttt{\#ifndef...\#define...}) exist as a preprocessor check (or include guard, a term often used in the industry), they ensure that the declarations within this header file are processed only once per compilation. If \texttt{MOTORCONTROL\_H} has not been defined during the compilation of a particular .cpp file, the preprocessor includes the subsequent lines. These lines contain the declarations for other parts of the program to interact with the motor control module, such as function prototypes (e.g., \texttt{void motorSetup()}), enumeration definitions (\texttt{enum MotorStatus}), and external variable declarations (\texttt{extern const int OneChamber}). The actual implementations (definitions) for these prototyped functions are in the corresponding \texttt{motorcontrol.cpp} file, which is compiled separately and later linked with machine code generated from other files.

\begin{lstlisting}[style=cppstyle, caption={Header for Motor Control Interface}, label={lst:motorcontrolh}]
	#ifndef MOTORCONTROL_H
	#define MOTORCONTROL_H
	
	#include <Arduino.h>
	
	extern const int OneChamber;          // 1/8 revolution, exported for BLE layer
	enum MotorStatus { MOTOR_IDLE, MOTOR_RUNNING, MOTOR_JUST_COMPLETED };
	void motorSetup();                    // call once from setup()
	bool motorStartDispense(int numSteps); // returns true if motor accepted the job
	
	MotorStatus motorLoop();
	// ...
	
	#endif // MOTORCONTROL_H
\end{lstlisting}
Having covered the structure of the files responsible for handling motor controls, it is time to look at an actual implementation within the \textbf{motorcontrol.cpp} file, as seen in this code block \ref{lst:motorcontrolcpp}. The file begins with inclusion of libraries. \texttt{motorcontrol.h} is the accompanying header file containing function prototypes, \texttt{Stepper.h} library is a built-in Arduino library for high-level stepper motor control. 

After libraries come 2 \textit{const} variables needed to calculate rotation (code block \ref{lst:motorcontrolcpp}, lines 4 and 5). According to the 28BYJ-48 documentation \cite{stepper}, it has Speed Variation Ratio 1/64 and Stride Angle 5.625deg /64 (it is usually denoted for half-step mode, so full-step mode would be 1/32), which essentially means that inside this motor, there is an internal gear connected to an external gear that rotates the shaft, connected with a 1-to-64 gear reduction, but the internal gear also steps 1/64th of a rotation each time coil polarisation changes. It means that total amount of steps for the full rotation of the shaft is 64*64=4096 , which gives us the value for the \texttt{const int stepsPerRevolution = 2048;}. To calculate \texttt{const int OneChamber = stepsPerRevolution / 8;}, gear ratio of designed device should be taken into consideration. As mentioned in the previous section, the inner ring of the Mill contains 88 teeth, while gear that is attached to the stepper motor has 32 teeth. Since there are 22 Chambers in total, each chamber corresponds to exactly 4 teeth of rotation (teeth are equal for both motor and Mill gears). 

Next is the definition of the pins that are attached to the wires that drive the stepper motor (lines 7 to 10) and then (line 12) \texttt{Stepper} class of the \texttt{Stepper.h} library. It takes as an input amount of steps and energizing leads. After the class, helper variables are declared. They serve utility functions such as state change in the code. We will review their purpose when they appear in functions. 

After establishing the structure, the functions are declared:
\begin{itemize}
	\item \textbf{deenergizeStepper()} function that depowers wires when they are not in use, since methods of the \texttt{Stepper} class don't do that. It is an important function for saving energy, as constant current to the coils will drain battery charge very fast.
	\item \textbf{motorSetup()} function initializes the motor. Since it only takes speed as an input, there is not much else to initialize, but it also has output lines to check whether operation has been correctly done.
	\item \textbf{motorStartDispense(int numSteps)}  function serves as the primary interface to initiate a motor rotation. It rotates the Pill Dispenser exactly one chamber. It has a precondition \texttt{if (!isStepping)}: it will not do anything if motor is already in process of rotating. It takes an integer \texttt{numSteps} as input, specifying how many steps the motor should turn. 
\end{itemize}
Next, \texttt{MotorStatus motorLoop()}. The \texttt{MotorStatus} is a function of an \textit{enum} type, which means it can only a predetermined set of values. It which serves the purpose of state-selector. It is defined in the \textbf{motorcontrol.h} file (seen here: \ref{lst:motorcontrolh}, on line 7). The logic for state-change is defined in the \texttt{motorLoop()} variable. Graphically, the controlling logic can be seen on image \ref{fig:screenshot18}. The loop works as follows:

\begin{itemize}
	\item \textbf{Top-level availability test}\\
	The \texttt{if (isStepping)} decides whether the motor currently has
	work to do.  
	\begin{itemize}
		\item \texttt{false} $\Rightarrow$ return
		\texttt{MOTOR\_IDLE}.
		\item \texttt{true}  $\Rightarrow$ proceed to timing check.
	\end{itemize}
	
	\item \textbf{Timing check}\\
	Evaluate \texttt{millis() - lastStepTime \(\ge\) stepInterval}.
	\begin{itemize}
		\item \texttt{false} (interval not yet elapsed)  
		$\Rightarrow$ return \texttt{MOTOR\_RUNNING} to signal
		the dispense is ongoing but no step is taken in this
		call.
		\item \texttt{true}  (interval elapsed) $\Rightarrow$
		readiness for a potential step.
	\end{itemize}
	
	\item \textbf{Step-or-finish decision}\\
	Check \texttt{stepsRemaining > 0}.
	\begin{itemize}
		\item \texttt{stepsRemaining > 0}:  
		\begin{itemize}
			\item execute \texttt{myStepper.step(1)};
			\item decrement \texttt{stepsRemaining};
			\item update \texttt{lastStepTime};
			\item return \texttt{MOTOR\_RUNNING}.
		\end{itemize}
		\item \texttt{stepsRemaining \(\le\) 0}:  
		\begin{itemize}
			\item set \texttt{isStepping} to \texttt{false};
			\item call \texttt{deenergizeStepper()};
			\item return \texttt{MOTOR\_JUST\_COMPLETED}.
		\end{itemize}
	\end{itemize}
\end{itemize}
Note that it is not a recursive loop, it doesn't call itself. This function is called from \texttt{void loop()} function of the \textbf{main.cpp} file.

\begin{lstlisting}[style=cppstyle, caption={Implementation of Motor Control Interface}, label={lst:motorcontrolcpp}]
#include "motorcontrol.h"
#include <Stepper.h>

const int stepsPerRevolution = 4096;
const int OneChamber          = stepsPerRevolution / 8;

const int in1Pin = 4;
const int in2Pin = 5;
const int in3Pin = 6;
const int in4Pin = 7;

static Stepper myStepper(stepsPerRevolution, in1Pin, in2Pin, in3Pin, in4Pin);

static bool          isStepping     = false;
static int           stepsRemaining = 0;
static unsigned long lastStepTime   = 0;
static const unsigned long stepInterval = 2; // ms

static void deenergizeStepper() {
	digitalWrite(in1Pin, LOW);
	digitalWrite(in2Pin, LOW);
	digitalWrite(in3Pin, LOW);
	digitalWrite(in4Pin, LOW);
	Serial.println("Stepper coils de-energized.");
}

void motorSetup() {
	Serial.println("Initializing Stepper Motor...");
	myStepper.setSpeed(10);
	Serial.println("Stepper Motor Initialized.");
}

bool motorStartDispense(int numSteps) {
	if (!isStepping) {
		Serial.printf("Starting dispense of %d steps.\n", numSteps);
		stepsRemaining = numSteps;
		isStepping    = true;
		return true;
	}
	return false;
}

MotorStatus motorLoop() {
	if (isStepping) {
		if (millis() - lastStepTime >= stepInterval) {
			if (stepsRemaining > 0) {
				myStepper.step(1);
				stepsRemaining--;
				lastStepTime = millis();
				return MOTOR_RUNNING;
			} else {
				isStepping = false;
				deenergizeStepper();
				Serial.println("Dispense complete.");
				return MOTOR_JUST_COMPLETED; // Signal completion
			}
		}
		return MOTOR_RUNNING; // Still stepping or waiting for interval
	}
	return MOTOR_IDLE; // Not stepping
}

\end{lstlisting}

Before doing so, the fundamentals of Bluetooth, and particularly \ac{BLE} must be covered. Bluetooth standard was initially covered under IEEE 802.15.1 Task group \cite{1016473}, which defined the physical layer and \ac{MAC} (layers 1 and 2 of the \ac{OSI} model, respectively) implementation of this communication protocol. Currently it is maintained by Bluetooth Special Interest Group (SIG), which has developed a \ac{BLE} extension protocol, which is used in this thesis. The functional principles of this protocol are thoroughly documented in the Bluetooth Low Energy Primer\cite{ble_primer_2024}. All definitions will be taken from this document, with additions on how they relate to this project. To cover the implementation of \ac{BLE} communication of device with an Android App, some definitions need to be established:
\begin{itemize}
	\item \textbf{Bluetooth Low Energy} is a wireless communication protocol designed for short-range communication with very low power consumption, making it ideal for battery-operated devices. 
	\item \textbf{Central (Client)} is the device that initiates a connection and requests data. In this case, this is the Android App. Centrals scan for peripherals.
	\item \textbf{Peripheral (Server)} is the device that advertises its presence and provides data. In this case, this is ESP32 Pill Dispenser. Peripherals wait for a central to connect.
	\item \textbf{Advertising} is the process by which a peripheral broadcasts small packets of data to announce its presence, services, and device name. This allows centrals to discover it. 
	\item \textbf{Scanning} is the process by which a central listens for advertising packets from peripherals.
	\item \textbf{Connection} is he establishment of a link between a central and a peripheral after discovery through advertising and scanning.
	\item \textbf{Device Name} is a human-readable name a device advertises, in this case it is "PillDispenserESP32".
	\item \textbf{Device Address (MAC Address)} is a unique hardware identifier for a Bluetooth device.
\end{itemize}
The main unit of communication and crucial part of the protocols structure is the \ac{GATT} profile. While \ac{GATT} is part of \ac{BLE} protocol, it has many terms associated directly with it, as seen on image \ref{fig:screenshot19}. The associated terms are described as follows:
\begin{itemize}
	\item \textbf{Generic Attribute Profile} or \ac{GATT}, Defines high level data types known as services, characteristics and descriptors in terms of underlying attributes in the attribute table.
	\item \textbf{Profile} Profile specifications define the roles that related devices (like the smartwatch and key fob) assume and in particular, define the behaviour of the client device and the data on the connected server that it should work with. In case of this thesis, a custom profile has been implemented, through the services and characteristics that have been defined.
	\item \textbf{Service} A service specification defines a single service along with the characteristics and descriptors that it contains. The behaviours to be exhibited by the device hosting the service in response to various conditions and state data values are defined in the service specification.
	\item \textbf{Characteristic} Characteristics are individual items of state data and have a type, an associated value and a set of properties which indicate how the data may be used in terms of sets of related GATT procedures.
	\item \textbf{Value} The attribute value field is a byte array contain the attribute’s value. Interpretation of the byte array both in terms of data types and semantics is the concern of higher layers of the stack.
	\item \textbf{Properties} Define what operations a client can perform on a characteristic's value (Read, Write, Write Without Response, Notify, Indicate). 
	\item \textbf{UUID} all services, characteristics and descriptors have a \ac{UUID} which identifies the type of the service, characteristic or descriptor to which it relates rather than a particular instance on a particular device.
	\item \textbf{Descriptor} Descriptors belong to some characteristics and can contain metadata like a textual description for the characteristic or might provide some means of controlling the behaviour of a characteristic. Characteristics have zero or more descriptors attached to them.
	\item \textbf{CCCD} Any characteristic supporting notifications or indications must have a client characteristic configuration descriptor because its value (which clients may write to) controls whether or not notifications or indications are currently enabled or not.
\end{itemize}
Additionally, all \ac{BLE} Operations can be categorized in 3 groups:
\begin{itemize}
	\item \textbf{Read Operation} when the central requests the value of a characteristic from the peripheral
	\item \textbf{Write Operation} when the central sends data to the peripheral to set the value of a characteristic
	\item \textbf{Notification Subscription} when the central enables notifications on a characteristic (by writing to its \ac{CCCD}) to receive updates when its value changes.
\end{itemize}

Next, the actual implementation of \ac{BLE} interface shall be covered. The code block \ref{lst:BToothcpp1} provides the definition and initialization part.  Firstly, preprocessor directives to include other files: 
\begin{itemize}
	\item \texttt{BTooth.h} is the header file for this file;
	\item \texttt{motorcontrol.h} used for manual dispense;
	\item \texttt{Arduino.h} used extensively for many tasks such as \texttt{Serial.println()}
	\item \texttt{NimBLEDevice.h} is is the header for the NimBLE Arduino library, which provides Bluetooth Low Energy (BLE) functionality for ESP32;
	\texttt{Preferences.h} provides an easy way to use the ESP32's non-volatile storage to save data that persists even after the ESP32 is restarted or powered off
\end{itemize}
After that, Service and Characteristic \ac{UUID}s are declared. Their values are not as relevant as long as they are unique and existing. What is relevant, however, is what purpose they serve. This is important because \ac{BLE} protocol has limited capacity for these \ac{UUID}s, which can lead to issues, such as Android App failing to fetch all characteristics. The implemented characteristics serve this purpose:
\begin{description}[style=nextline] % label on its own line
	% ------------ WRITABLE -------------
	\item[\textbf{Writable}]%
	\leavevmode\\[-0.8\baselineskip] % ←-- forces break, trims extra gap
	\begin{itemize}
		\item \texttt{Set\_Device\_Time} — synchronize the ESP32 clock.
		\item \texttt{Set\_Dispense\_Schedule} — add, edit, or delete schedule entries.
		\item \texttt{Trigger\_Manual\_Dispense} — manually trigger a dispense (logged for traceability).
	\end{itemize}
	
	% ------------ READABLE -------------
	\item[\textbf{Readable}]%
	\leavevmode\\[-0.8\baselineskip]
	\begin{itemize}
		\item \texttt{Get\_Device\_Time} — read the current device time.
		\item \texttt{Get\_Dispense\_Schedule} — retrieve the stored schedule.
		\item \texttt{Get\_Last\_Dispense\_Info} — timestamp + status of the last event.
		\item \texttt{Get\_Time\_Until\_Next\_Dispense} — countdown to the next dose.
		\item \texttt{Get\_Dispense\_Log} — full dispense history.
	\end{itemize}
\end{description}
As seen in the code block \ref{lst:BToothcpp1}, there is a naming convention in place. For \ac{UUID}s it is \texttt{CHAR"\_CHARACTERISTIC\_PURPOSE"\_UUID} except for \texttt{SERVICE\_UUID} which is a service and not a characteristic, therefore it doesn't have \texttt{CHAR} prefix. The pointers to these characteristics are initialized as null-pointers i.e. without an address. \texttt{Static} means that they can be accessed anywhere within this file, but cannot be accessed from without. The naming convention for pointers is \texttt{p"CharacteristicPurpose"Characteristic}.
